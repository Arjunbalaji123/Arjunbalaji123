## 🛡️ Federated Learning-Based Network IDS

### The Problem

Traditional centralized intrusion detection can require network
traffic from multiple organizations to be collected centrally.

### The Approach

Simulate multiple participants training local intrusion detection
models and exchanging model updates rather than raw traffic.

### Detection Pipeline

```text
NETWORK TRAFFIC
       ↓
FEATURE EXTRACTION
       ↓
LOCAL DATASET
       ↓
LOCAL IDS MODEL
       ↓
LOCAL TRAINING
       ↓
MODEL UPDATE
       ↓
FEDERATED AGGREGATION
       ↓
GLOBAL IDS MODEL
       ↓
ATTACK / BENIGN PREDICTION
```

### Engineering Focus

* Network traffic analysis
* Machine learning
* Intrusion detection
* Federated learning
* Model aggregation
* Attack classification
* Model evaluation

### Engineering Question

> Can distributed organizations improve a shared intrusion detector
> without directly sharing their raw network traffic?

# `04` — ENGINEERING DECISIONS

One principle guides my projects:

> **Knowing why a technology was chosen matters more than simply
> knowing how to use it.**

For important projects, I document decisions around:

```text
Architecture
     ↓
Database
     ↓
API Design
     ↓
Security
     ↓
Performance
     ↓
Machine Learning
     ↓
Scalability
```

### Questions I ask

**Why this database?**

* What relationships exist?
* What queries matter?
* Is consistency important?
* How will the schema evolve?

**Why this architecture?**

* Is it maintainable?
* Is it unnecessarily complex?
* Can another developer understand it?
* Can it evolve?

**Why this ML model?**

* Does it fit the data?
* Is it appropriate for the problem?
* How interpretable is it?
* How does it compare with alternatives?

**Why this frontend architecture?**

* How should state be managed?
* How reusable are the components?
* How should data flow through the application?

I don't want to use a technology because it is popular.

I want to understand **why it belongs in the system.**
